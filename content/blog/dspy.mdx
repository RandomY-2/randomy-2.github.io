## Introduction

Language models let researchers build NLP systems at higher levels of abstraction and with lower data requirements than before. That has produced an exploding space of prompting techniques — and lightweight finetuning techniques — for adapting LMs to new tasks, eliciting systematic reasoning, and augmenting them with retrieved sources or tools. Most of these techniques are explored in isolation, but interest has grown in multi-stage pipelines and agents that decompose complex tasks into more manageable LM calls.

LMs are sensitive to how they are prompted, and this is worse in pipelines where multiple calls have to interact. As a result, LM calls in existing pipelines and developer frameworks are generally implemented with hard-coded prompt templates: long strings of instructions and demonstrations hand-crafted by trial and error. That approach is brittle and unscalable — conceptually akin to hand-tuning the weights of a classifier. A given string prompt might not generalize to different pipelines, LMs, data domains, or even inputs.

DSPy (pronounced dee-ess-pie; the second iteration of Demonstrate–Search–Predict) pushes building LM pipelines away from manipulating free-form strings and closer to programming: composing modular operators into **text transformation graphs**, where a compiler automatically generates optimized LM invocation strategies and prompts from a program. The inspiration is the consensus that emerged around neural network abstractions: (1) many general-purpose layers can be modularly composed in any architecture, and (2) weights can be trained with optimizers instead of being hand-tuned.

String-based prompting techniques, including task-dependent ones like Chain of Thought and ReAct, are translated into **declarative modules** that carry natural-language typed **signatures**. Modules are task-adaptive components — akin to neural network layers — that abstract a text transformation such as answering a question or summarizing a paper. Each module is **parameterized** so that it can learn its desired behavior by iteratively bootstrapping useful demonstrations within the pipeline. Inspired by PyTorch, modules are used via define-by-run computational graphs. A pipeline is expressed by declaring the modules needed and using them in any logical control flow.

The **DSPy compiler** then optimizes any program to improve quality or cost. Its inputs are the program, a few training inputs with optional labels, and a validation metric. It simulates versions of the program on the inputs and bootstraps example traces of each module, using them to construct effective few-shot prompts or to finetune small LMs for steps of the pipeline. Optimization is conducted by **teleprompters** — general-purpose strategies that determine how the modules should learn from data. The compiler maps declarative modules to high-quality compositions of prompting, finetuning, reasoning, and augmentation.

The evaluation focus is the role of expert-crafted prompts in shaping system performance. Two case studies — math word problems (GSM8K) and multi-hop question answering (HotPotQA) — explore chain of thought, multi-chain reflection, multi-hop retrieval, retrieval-augmented QA, and agent loops. Straightforward DSPy programs outperform systems that use hand-crafted prompts, and they let much smaller LMs be used effectively.

This is the first programming model that translates prompting techniques into parameterized declarative modules and introduces a compiler with general optimization strategies for arbitrary pipelines of those modules. Very short programs can bootstrap self-improving multi-stage systems using LMs as small as Llama2-13b-chat and T5-Large (770M parameters). Without hand-crafted prompts, and within minutes to tens of minutes of compiling, compositions of DSPy modules raise quality from 33% to 82% and from 32% to 46% for GPT-3.5, and from 9% to 47% and from 22% to 41% for Llama2-13b-chat.

## The DSPy Programming Model

LMs are treated as abstract devices for text generation — a promptable in-context learner (GPT-3.5, Llama2) or a smaller finetunable model (T5-base). A default LM is selected; operations use it unless configured otherwise. Programs are Python functions from task input to output after a series of steps.

Three abstractions enable automatic optimization:

* **Signatures** abstract the input/output behavior of a module.
* **Modules** replace hand-prompting techniques and compose into arbitrary pipelines.
* **Teleprompters** optimize all modules in the pipeline to maximize a metric.

### Natural Language Signatures can abstract prompting and finetuning

Instead of free-form string prompts, programs use natural-language signatures to assign work to the LM. A signature is a natural-language typed declaration of a function: a short declarative spec of *what* a text transformation needs to do ("consume questions and return answers"), not *how* a specific LM should be prompted. Formally, a signature is a tuple of input fields and output fields, plus an optional instruction. A field has a name and optional metadata. Roles are typically inferred from field names: the compiler uses in-context learning to interpret `question` differently from `answer` and iteratively refines that usage.

Signatures have two benefits over prompts. They compile into self-improving, pipeline-adaptive prompts or finetunes — primarily by bootstrapping useful demonstrating examples. They also handle structured formatting and parsing, reducing brittle string manipulation in user programs.

```python
qa = dspy.Predict("question -> answer")
qa(question="Where is Guaraní spoken?")
# Prediction(answer='Guaraní is spoken mainly in South America.')
```

Field names indicate semantic roles. DSPy expands them into instructions, so `english_document -> french_translation` prompts for English-to-French translation. More explicit constraints are available when needed.

### Parameterized and templated Modules can abstract prompting techniques

A signature defines an interface. To use it, a module is declared with that signature; the declaration returns a function having that signature.

**The Predict module.** The core module. Internally it stores the signature, an optional LM override, and a list of demonstrations (initially empty). Like a PyTorch layer, the instantiated module is a callable: it takes keyword arguments for the input fields, formats a prompt that implements the signature and includes demonstrations, calls the LM, and parses the output fields. In compile mode it tracks input/output traces to assist the teleprompter.

**Other built-in modules.** Prompting techniques become modular functions that support any signature — unlike prompting an LM with task-specific hand-written few-shot examples. Built-ins include `ChainOfThought`, `ProgramOfThought`, `MultiChainComparison`, and `ReAct`. They are interchangeable implementations of a signature: changing `Predict` to `ChainOfThought` produces a system that thinks step by step before committing to its output field.

These modules are a few lines of code that expand the user-defined signature and call `Predict` one or more times. A simplified `ChainOfThought`:

```python
class ChainOfThought(dspy.Module):
    def __init__(self, signature):
        rationale_field = dspy.OutputField(
            prefix="Reasoning: Let's think step by step."
        )
        signature = dspy.Signature(signature).prepend_output_field(rationale_field)
        self.predict = dspy.Predict(signature)

    def forward(self, **kwargs):
        return self.predict(**kwargs)
```

This is a fully-fledged module capable of learning effective few-shot prompting for any LM or task.

**Parameterization.** Any LM call that implements a signature must specify (1) which LM to call, (2) prompt instructions and field prefixes, and (3) the demonstrations used as few-shot prompts (frozen LMs) or as training data (finetuning). The compiler focuses on automatically generating and selecting useful demonstrations. Bootstrapping good demonstrations is a systematic way to teach sophisticated pipelines new behaviors.

**Tools.** Modules that execute computation. Retrieval is `dspy.Retrieve`, with built-in support for ColBERTv2, Pyserini, and Pinecone. Experimental tools include SQL execution and a sandboxed Python interpreter.

**Programs.** Modules compose in a define-by-run interface. Modules needed are declared at initialization so DSPy can track them for optimization; the pipeline is arbitrary code in `forward`. A complete retrieval-augmented generation system:

```python
class RAG(dspy.Module):
    def __init__(self, num_passages=3):
        self.retrieve = dspy.Retrieve(k=num_passages)
        self.generate_answer = dspy.ChainOfThought("context, question -> answer")

    def forward(self, question):
        context = self.retrieve(question).passages
        return self.generate_answer(context=context, question=question)
```

`ChainOfThought` is a drop-in replacement for `Predict`. Changing the signature to `context, question -> search_query` yields a system that generates search queries rather than answers.

### Teleprompters can automate prompting for arbitrary pipelines

A teleprompter is an optimizer that takes a program, a training set, and a metric, and returns a new optimized program. Different teleprompters apply different strategies.

Training sets may be small — a handful of examples — though larger data enables more powerful optimization. Examples may be incomplete: only inputs are required. Labels for intermediate pipeline steps are not required unless the metric uses them. Typically only the program's final output is labeled. That label-efficiency is critical for modularity: a new pipeline is recompiled, not re-annotated.

Metrics can be exact match or F1, or entire DSPy programs that balance multiple concerns. Compiling the RAG module against question–answer pairs with exact match:

```python
qa_trainset = [dspy.Example(question="What is the capital of France?", answer="Paris")]
teleprompter = dspy.BootstrapFewShot(metric=dspy.evaluate.answer_exact_match)
compiled_rag = teleprompter.compile(RAG(), trainset=qa_trainset)
```

`BootstrapFewShot` simulates RAG on the training examples and collects demonstrations of each module that collectively lead to valid output — traces that respect the signatures and the metric. A custom metric can additionally require the prediction to be a substring of some retrieved passage. Behavior like faithful grounding can itself be checked by another DSPy program.

Teleprompters compose via a **teacher** program from which demonstrations are sampled. Expensive programs (complex ensembles of large LMs) can supervise cheap ones (simple pipelines of smaller LMs). A compiled RAG using Llama2-13b-chat can teach a `BootstrapFinetune` run that produces an efficient Flan-T5-large program, using unlabeled questions and a grounding metric to filter ungrounded answers.

## The DSPy Compiler

Compiling automatically optimizes any program. Prompting and finetuning are unified. Typical teleprompters go through three stages.

**Stage 1: Candidate generation.** The compiler recursively finds all unique `Predict` modules, including those nested under other modules. For each predictor it may generate candidate values for instructions, field descriptions, or — most importantly — demonstrations. Simple rejection-sampling-like approaches bootstrap highly effective multi-stage systems.

`BootstrapFewShot` simulates a teacher (or, if unset, the zero-shot version of the program) on training inputs, possibly several times at high temperature. In compile mode, multi-stage traces are tracked throughout execution. The metric filters traces that help the pipeline pass. Bad examples are thrown away; good examples become potential demonstrations.

**Stage 2: Parameter optimization.** Each parameter now has a discrete set of candidates. Hyperparameter tuners — random search, or Tree-structured Parzen Estimators as in HyperOpt and Optuna — select among them. `BootstrapFewShotWithRandomSearch` and `BootstrapFewShotWithOptuna` implement this. `BootstrapFinetune` uses the demonstrations to update LM weights for each predictor, replacing that module's LM with the new weights. The objective is average quality under the metric, typically with cross-validation. This applies even with no labels for any stage, depending on the metric.

**Stage 3: Higher-order program optimization.** The compiler can also modify control flow. The simplest form used here is ensembles: bootstrap multiple copies of the same program, then replace it with a program that runs them in parallel and reduces predictions with a custom function (e.g. majority voting). Future work can accommodate test-time bootstrapping and automatic backtracking.
